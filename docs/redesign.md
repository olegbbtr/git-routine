# git-routine: редизайн

Статус: согласовано 2026-11-02. Заменяет вариант с Neon (`redesign-neon.md`, удален).

## 1. Решения

- Источник истины - git-репозиторий с данными (`git-route-storage-prod`).
- Сервера нет. Клиент пишет в GitHub сам через Contents API.
- Охват: только таймер рутин.
- Доступ: пользователи с ролями (owner, writer, contributor, reader, guest), fine-grained токены только на репозиторий данных, реестр `users/` в том же репозитории, опциональное E2E. Только GitHub Free, без Actions.

Что исправляется:

| Проблема | Причина | Решение |
| --- | --- | --- |
| Конфликты и потеря истории | Общий `history.json` перезаписывается целиком | Файл на запуск, новые файлы не конфликтуют |
| Удаления не доходят | Pull не смотрит на исчезнувшие файлы | Чтение по дереву репозитория, отсутствующее = удаленное |
| Кириллица ломается | `atob` без UTF-8 декодирования | `TextDecoder` |
| Классический PAT ко всем репозиториям | Настройки просят "contents read/write" без ограничения | Fine-grained PAT только на репозиторий данных |
| Неудобно править | Только дерево в UI, JSON в репозитории | YAML в репозитории, текстовый режим в UI |
| Бесполезная история | Пишется любой выход, время по часам | Статус, активное время и паузы раздельно, статистика |

## 2. Формат репозитория данных

```
routines/<slug>.yaml
runs/<YYYY>/<MM>/<YYYYMMDDTHHMMSSZ>-<id>.json
space.json                          # режим: {"e2e": false}
users/<user-id>.json
keys/<epoch>/...                    # только при E2E
.grants/<device-id>.json            # выданные права, зашифрованы для устройства
.rotation/<device-id>.json          # только во время ротации
```

### Рутина

```yaml
name: 3. Warmup
steps:
  - Set 1:
      - Head tilts: 20s
      - Head turns: 20s
      - Chin tucks: 20s
  - Set 2:
      repeat: 2
      steps:
        - Arm rotations: 20s
        - Break: 30s wait
```

Правила:

- элемент списка - словарь из одного ключа: метка → значение;
- значение-строка → шаг:
  - интервал: `20s`, `5m`, `1m30s`;
  - интервал с подтверждением: `30s wait` - после отсчета ждать нажатия (в старом формате `pause: true`);
  - действие: `wait` - без времени, ждать нажатия "сделано", время замеряется;
- значение-список → блок с `repeat: 1`;
- значение-словарь `{repeat, steps}` → блок с повторами;
- значение-словарь `{parallel: [...]}` → параллельные ветки (минимум две): все стартуют вместе, блок заканчивается, когда закончились все. Сдвиг старта ветки - интервалом в ее начале:
  ```yaml
  - Гречка и зажарка:
      parallel:
        - Гречка:
            - Варить: 15m
            - Настоять: 5m
        - Зажарка:
            - Нарезать лук: wait
            - Обжарить: 5m
  ```
- модель в коде: `src/format/model.ts` (interval, action, group, parallel); старый формат конвертируется через `fromLegacy`;
- выполнение: плоский список шагов (`flatten`) параллель не выражает → на этапе 3 таймер переписывается на движок-автомат по веткам с отсчетом по часам. Это же дает надежную работу в фоне (UC5) и состояние, которое можно передать на дисплей по P2P (UC3);
- slug файла задается при создании и не меняется при переименовании рутины; переименование меняет только `name`.

Поля `created`, `edited`, `executed` из рутины убираются: даты правок есть в git, последний запуск вычисляется из `runs/`. Сейчас каждый запуск модифицирует рутину (`executed`), что порождает лишние коммиты и конфликты.

### Запуск

```json
{
  "id": "ab12cd34",
  "routine": "warmup",
  "routineName": "3. Warmup",
  "startedAt": "2026-11-02T15:30:00Z",
  "finishedAt": "2026-11-02T15:36:07Z",
  "status": "completed",
  "activeSeconds": 352,
  "pausedSeconds": 15,
  "device": "d-7f3a"
}
```

- `status`: `completed` или `aborted`;
- `id` генерирует клиент, он же в имени файла → повторная отправка не создает дубль;
- шаги (план и факт) - позже, если понадобятся.

## 3. Синхронизация

Чтение:

1. `GET /repos/{repo}/branches/{branch}` с `If-None-Match` → `304`, если ничего не менялось (не тратит лимит).
2. Иначе `GET /git/trees/{sha}?recursive=1` → все пути и sha блобов.
3. Скачать только блобы, чьи sha изменились (`GET /git/blobs/{sha}`), декодировать base64 → UTF-8.
4. Пути, которых больше нет в дереве, удалить из локального кэша.

Запись:

- **Запуск:** `PUT contents/runs/...` без `sha`. Ответ "файл уже существует" (422) = успех. `409` = гонка с другим коммитом → повтор с задержкой.
- **Рутина:** `PUT` с `sha` версии, от которой начиналась правка. `409` → конфликт, UI показывает обе версии: "Взять ту", "Оставить мою".
- **Удаление рутины:** `DELETE` с `sha`, конфликт обрабатывается так же.

Офлайн: запуски попадают в outbox (localStorage) и отправляются при появлении сети и при каждом синке. Значок синка: "✓" или "↑ N".

Кэш: последнее дерево и содержимое файлов в localStorage → приложение открывается мгновенно и работает без сети.

## 4. Пользователи и доступ

Ограничения, из которых исходит схема: только GitHub Free, без Actions (условия GitHub запрещают использовать Actions как часть serverless-приложения), все токены - fine-grained и только на репозиторий данных.

### Режим репозитория

`space.json` в корне: `{"version": 1, "e2e": false}`. Режим задается при создании и влияет на две вещи: что видит держатель токена и сколько нужно токенов.

| | Без E2E | С E2E |
| --- | --- | --- |
| Что лежит в git | Открытые YAML и JSON | Шифротекст (раздел 4.8) |
| Кто читает | Любой держатель токена с Contents: read | Только устройства, получившие ключ |
| Права на чтение | Весь репозиторий | По ключам: можно ограничить часть данных |
| Токены reader и contributor | По одному на человека: отключение = отзыв | Общие: отключение = смена ключей |
| Читаемость для агента и редактора | Полная | Только через приложение или CLI-устройство |

### Роли и токены

| Роль | Права токена | Может | Токенов |
| --- | --- | --- | --- |
| `owner` | Токен `main`: Contents: write; позже по необходимости + Variables: write, Issues: write | Все: данные, пользователи, приглашения, обработка предложений | 1, общий для устройств владельца |
| `writer` | Contents: write | Писать данные | По одному на человека |
| `contributor` | Contents: read, Commit statuses: write, Issues: write | Читать, предлагать и комментировать через Inbox | Без E2E - на человека; с E2E - 1 общий |
| `reader` | Contents: read, Commit statuses: write | Читать | Без E2E - на человека; с E2E - 1 общий |
| `guest` | Нет | То, что передает хост по WebRTC, пока он онлайн | 0 |

Служебный токен:

| Токен | Права | Для чего | Штук |
| --- | --- | --- | --- |
| `invite` | Variables: read | В permanent link: прочитать зашифрованный пакет приглашения | 1 на все приглашения |

Свойства:

- `reader`, `contributor`, `invite` ничего не могут испортить: это ограничивает сам GitHub.
- `writer` технически может перезаписать историю (защита веток на приватных - только в Pro). Давать только доверенным; страховка - зеркало (4.9).
- `Commit statuses: write` у `reader` и `contributor` - канал записи без права на файлы: регистрация устройства (публичный ключ P-256 в base64, ~88 символов, помещается в описание статуса) и подтверждения ("переключился на новый токен").
- `Variables: write` - только у owner: иначе участник мог бы удалить чужие приглашения.
- Все токены владелец создает вручную на GitHub (API для fine-grained PAT нет), но только по мере надобности: на старте один `main`. Максимум: без E2E - main, invite и по одному на участника; с E2E - 4 общих (main, invite, reader, contributor) и по одному на каждого writer.
- Срок токена = срок доступа.
- Лимит API, насколько известно, общий на аккаунт владельца.

### Постепенное усложнение

Начинаем с одного токена `main`. Остальные приложение предлагает создать только тогда, когда пользователь впервые делает то, что без них невозможно, и объясняет зачем.

| Уровень | Токены | Что работает |
| --- | --- | --- |
| 0. Только `main` | `main` (Contents: write) | Все свое: рутины, запуски, синк; свои новые устройства по QR; гости по session link |
| 1. Первое приглашение человека | + `invite`, + токен роли | Permanent link для других людей |
| 2. Первое предложение через Inbox | + право Issues: write у `main`, + `contributor` | Роль contributor |
| 3. Первый writer | + персональный токен writer | Роль writer |

Как это выглядит:

- **Свое новое устройство на уровне 0:** QR на подключенном устройстве содержит токен `main`, зашифрованный секретом из той же ссылки, плюс короткий PIN на экране. Пакет целиком в ссылке, переменные и `invite` не нужны. Устройства рядом, поэтому сверка кода - визуальная.
- **Первое приглашение другого человека:** "Чтобы пригласить Аню как reader, нужно: (1) токен для одноразовых ссылок - создается один раз; (2) токен reader - [без E2E: для Ани / с E2E: общий для всех читателей]. Создать?" → две ссылки на GitHub с заполненными полями → вставить.
- **Новые права для `main`:** если функции нужно право, которого нет у `main` (Variables: write для приглашений, Issues: write для Inbox), приложение ведет на страницу редактирования токена: fine-grained токену можно добавить права без перевыпуска (проверить, что значение токена при этом не меняется). Приложение проверяет права после правки.
- **Отказ от сложного:** если человеку нужно только посмотреть или потренироваться вместе - приложение сначала предлагает session link, где токены не нужны.

Итог: пользователь, которому достаточно своих устройств и гостей, никогда не видит больше одного токена.

### Формат

```
users/<user-id>.json
```

```json
{
  "id": "u-oleg",
  "name": "Oleg",
  "role": "owner",
  "token": { "fingerprint": "sha256:1f3a...", "shared": false, "expiresAt": null },
  "devices": [
    { "id": "d-7f3a", "name": "Pixel 9 Pro", "publicKey": "<JWK>", "addedAt": "2026-11-02T15:00:00Z" }
  ],
  "addedAt": "2026-11-02T15:00:00Z",
  "signature": "<подпись устройства владельца>"
}
```

- `fingerprint` - хэш токена; сам токен в репозитории открыто не хранится.
- `shared: true` - общий токен роли (режим E2E).
- Записи `users/` подписывает устройство владельца. Неподписанные или измененные записи клиенты игнорируют.

### Первый запуск (владелец)

1. Настройки → "Подключить репозиторий" → выбрать режим: с E2E или без.
2. Ссылка на создание токена `main` с заполненными полями: только репозиторий данных, Contents: read/write, без срока или максимальный.
3. Вставить токен в форму входа (`autocomplete` → менеджер паролей сохранит).
4. Приложение создает пару ключей устройства (WebCrypto, неэкспортируемый приватный ключ в IndexedDB), при E2E - ключ хранилища и ключ восстановления (4.8), и коммитит `space.json` и `users/<id>.json`.

Остальные токены - по мере надобности (см. "Постепенное усложнение").

### Ссылки

QR - это та же ссылка: для того, кто рядом; ссылка - для мессенджера. Если сканировать не может сам приглашаемый (ТВ), QR показывает он, а сканирует хост.

| | Session link | Permanent link |
| --- | --- | --- |
| Адрес | `#/session?room=<id>&k=<секрет>` | `#/permanent?repo=<owner/repo>&i=<id>&t=<invite-токен>&k=<секрет>` |
| Дает | Вход в живую сессию хоста | Постоянный доступ: новый пользователь или новое устройство |
| Токен в ссылке | Нет | Только `invite` (Variables: read) |
| Использований | Много, пока идет сессия | Одно |
| Срок | До конца сессии | До первого использования или срока приглашения |
| Подтверждение | Каждого гостя или "впускать всех" | Каждое устройство, по коду |
| След в репозитории | Нет | Запись в `users/` |

#### Session link

1. Хост: "Session link" → уровень (смотреть, управлять, предлагать) → ссылка или QR.
2. Гость открывает → подключается к комнате по WebRTC (сигнализация Trystero, пароль комнаты из секрета) → хост видит "Гость, код 4F2A" → впускает.
3. Хост завершил сессию или закрыл приложение → ссылка не работает.

Гость видит только то, что передает хост (текущую рутину, идущий таймер), а не весь репозиторий. Права гостя не выше прав хоста. В одной сети соединение прямое, TURN не нужен.

#### Permanent link

Пакет приглашения лежит в **переменной репозитория** `INVITE_<id>`: у переменных нет истории, удаление окончательное. Файл в git не подходит: удаленный пакет остался бы в истории, и старая ссылка расшифровала бы его.

1. Хост: "Permanent link" → кто (новый пользователь или новое устройство существующего), роль, срок приглашения, по желанию PIN.
2. Устройство хоста собирает пакет:
   - токен роли не выше `reader` (`reader` или `contributor`);
   - без E2E: персональный токен, который владелец создал для этого человека; с E2E: общий токен роли.
   Пакет шифруется AES-GCM ключом из HKDF(секрет ссылки [+ PIN]) и записывается в `INVITE_<id>`.
3. Приглашаемый открывает ссылку → читает переменную токеном `invite` → расшифровывает → получает токен роли → создает пару ключей → регистрируется commit status-ом со своим публичным ключом и кодом проверки.
4. Хост при синке видит "Новое устройство у <имя>, код 4F2A-91C7" → сверяет код (голосом или в другом мессенджере) → подтверждает:
   - подписывает запись `users/`;
   - при E2E - заворачивает ключи хранилища для ключа устройства;
   - для роли `writer` - шифрует персональный токен writer ключом устройства → `.grants/<device-id>.json`;
   - удаляет `INVITE_<id>`.
5. Непринятое приглашение устройство хоста удаляет по сроку.

Свойства:

- Ссылка мертва после первого входа (как только хост синхронизировался) и по сроку.
- В ссылке и в мессенджере никогда нет ничего сильнее `invite`; `writer` и ключи E2E выдаются только после подтверждения, зашифрованными для устройства.
- Гонка до первого входа: кто первым открыл, тот получил пакет. Поэтому в пакете не выше `reader`, а с E2E без ключей он дает только шифротекст. PIN закрывает и это.
- Первое устройство владельца - исключение: токен вставляется вручную.

### Отключение

- **Пользователь с персональным токеном:** отозвать токен на GitHub → запись в `users/` помечается отключенной. Остальных не касается.
- **Пользователь с общим токеном (E2E):** пометить отключенным → новая эпоха ключей хранилища для оставшихся (4.8). Общий токен остается действующим, но без ключей дает только шифротекст. Общий токен перевыпускается редко, например раз в год или при подозрении на утечку.
- **Одно устройство пользователя** (у него несколько устройств):
  1. Новый токен с теми же правами (для общего - не нужен, достаточно эпохи ключей).
  2. Шифруется ключом каждого оставшегося устройства → `.rotation/<device-id>.json`.
  3. Устройства при синке забирают и отмечаются commit status-ом (это работает и для `reader`); затем старый токен отзывается.
  4. Не успевшее переключиться устройство - новое приглашение.

### E2E

Включается в `space.json`. Все на WebCrypto.

| Ключ | Что | Где |
| --- | --- | --- |
| Ключ устройства | ECDH P-256, приватная часть неэкспортируемая | IndexedDB; публичная - в `users/` |
| Ключ хранилища | AES-256-GCM, свой на каждую эпоху | `keys/<epoch>/<device-id>.json` - завернут для каждого устройства |
| Ключ восстановления | Случайные 128 бит | У владельца (1Password); `keys/<epoch>/recovery.json` |

- Файлы данных шифруются AES-256-GCM, AAD = путь файла + эпоха.
- Имена файлов не должны раскрывать содержимое: в режиме E2E рутины лежат как `routines/<случайный id>.json`, название и slug - внутри шифротекста.
- Сообщения коммитов в режиме E2E - без названий.
- Отключение пользователя или устройства → новая эпоха: новый ключ хранилища, завернутый для оставшихся устройств и для ключа восстановления. Перешифровывать все **не нужно**:
  - новые записи и любые изменяемые файлы шифруются новым ключом → отключенный их не прочитает;
  - неизмененные файлы остаются на старом ключе и перешифровываются при следующей правке (лениво);
  - массовое перешифрование почти ничего не дает: старые версии все равно лежат в истории git, а отключенное устройство обычно уже скачало все, к чему имело доступ. Отключенный сохраняет доступ ровно к тому, что мог читать до отключения, но не к новому;
  - кнопка "перешифровать все" - по желанию, одним коммитом, для случая, когда устройство было отключено до первой синхронизации.
- Ключи всех эпох хранятся завернутыми для актуальных устройств → новое устройство читает и старые файлы.
- Без ключа восстановления потеря всех устройств владельца = потеря данных: приложение не создаст хранилище E2E, пока ключ восстановления не сохранен и не введен повторно.
- Агент или CLI - отдельное устройство в `users/` со своим ключом.
- Что видно GitHub и при E2E: число и размеры файлов, время коммитов, реестр пользователей (имена устройств лучше тоже шифровать).

### Границы защиты

- Персональный токен удаленного пользователя действует до отзыва; общий - до эпохи ключей (дальше только шифротекст).
- `writer` может испортить данные, но не подделать `users/` и не скрыть порчу без перезаписи истории; от перезаписи - зеркало.
- Утечка токена не ограничена по времени, кроме его срока.
- Токены и ключи живут в хранилище браузера: очистка данных сайта → новое приглашение.
- Код приложения: если приложение раздается с GitHub Pages, E2E против GitHub не защищает от подмены кода. Для режима E2E - раздавать приложение не с GitHub (Cloudflare Pages, свой сервер) или из установленной PWA без автообновления.

### Зеркало

Регулярный `git fetch` репозитория данных на свой сервер (bublik или nl1, через infra) с refspec без `+`: перезапись истории не подхватывается, а вызывает уведомление.

## 5. UX

- **Главная:** список рутин из кэша, значок синка, под каждой рутиной - последний запуск и серия дней.
- **Таймер:** как сейчас (голос, бипы, wake lock). При выходе до конца: "Сохранить как прерванный?". Запуски короче 30 с не сохраняются.
- **Редактор:** дерево, как сейчас, плюс вкладка "Текст" (YAML). Валидация одной схемой для обеих вкладок.
- **История:** лента запусков, фильтр прерванных; на странице рутины - количество, серия, тепловая карта, среднее активное время. Все считается на клиенте.
- **Изменения извне:** после синка тост "Обновлено извне: 3. Warmup".
- **Настройки:** репозиторий, голос и звук, Пользователи (список, роли, устройства, последний синк, пригласить, отключить).

## 6. Миграция

Скрипт `scripts/migrate.mjs <путь к клону репозитория данных>`:

- `routines/*.json` → `routines/<slug>.yaml`; для кириллических названий slug транслитерируется;
- `history.json` → `runs/YYYY/MM/*.json`: `durationSeconds` → `activeSeconds`, `pausedSeconds: 0`, `status: completed`; записи короче 30 с - `aborted`; запись на 6211 с - `aborted` (явно аномальная);
- старые файлы удаляются;
- результат - один коммит, который вы проверяете и пушите.

`git-routine-storage` (тестовый) - архивировать.
