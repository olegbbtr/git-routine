# git-routine: редизайн

Статус: согласовано 2026-11-02. Заменяет вариант с Neon (`redesign-neon.md`, удален).

## 1. Решения

- Источник истины - git-репозиторий с данными (`git-route-storage-prod`).
- Сервера нет. Клиент пишет в GitHub сам через Contents API.
- Охват: только таймер рутин.
- Доступ: пользователи с ролями (owner, writer, suggester, reader), у каждого свой fine-grained токен на репозиторий данных; реестр `users/` в том же репозитории.

Что исправляется:

| Проблема | Причина | Решение |
| --- | --- | --- |
| Конфликты и потеря истории | Общий `history.json` перезаписывается целиком | Файл на запуск, новые файлы не конфликтуют |
| Удаления не доходят | Pull не смотрит на исчезнувшие файлы | Чтение по дереву репозитория, отсутствующее = удаленное |
| Кириллица ломается | `atob` без UTF-8 декодирования | `TextDecoder` |
| Классический PAT ко всем репозиториям | Настройки просят "contents read/write" без ограничения | Fine-grained PAT только на репозиторий данных |
| Неудобно править | Только дерево в UI, JSON в репозитории | YAML в репозитории, текстовый режим в UI |
| Бесполезная история | Пишется любой выход, время по часам | Статус, активное время и паузы раздельно, статистика |

## 2. Формат репозитория данных

```
routines/<slug>.yaml
runs/<YYYY>/<MM>/<YYYYMMDDTHHMMSSZ>-<id>.json
users/<user-id>.json
.rotation/<device-id>.json        # только во время ротации
```

### Рутина

```yaml
name: 3. Warmup
steps:
  - Set 1:
      - Head tilts: 20s
      - Head turns: 20s
      - Chin tucks: 20s
  - Set 2:
      repeat: 2
      steps:
        - Arm rotations: 20s
        - Break: 30s wait
```

Правила:

- элемент списка - словарь из одного ключа: метка → значение;
- значение-строка → шаг:
  - интервал: `20s`, `5m`, `1m30s`;
  - интервал с подтверждением: `30s wait` - после отсчета ждать нажатия (в старом формате `pause: true`);
  - действие: `wait` - без времени, ждать нажатия "сделано", время замеряется;
- значение-список → блок с `repeat: 1`;
- значение-словарь `{repeat, steps}` → блок с повторами;
- значение-словарь `{parallel: [...]}` → параллельные ветки (минимум две): все стартуют вместе, блок заканчивается, когда закончились все. Сдвиг старта ветки - интервалом в ее начале:
  ```yaml
  - Гречка и зажарка:
      parallel:
        - Гречка:
            - Варить: 15m
            - Настоять: 5m
        - Зажарка:
            - Нарезать лук: wait
            - Обжарить: 5m
  ```
- модель в коде: `src/format/model.ts` (interval, action, group, parallel); старый формат конвертируется через `fromLegacy`;
- выполнение: плоский список шагов (`flatten`) параллель не выражает → на этапе 3 таймер переписывается на движок-автомат по веткам с отсчетом по часам. Это же дает надежную работу в фоне (UC5) и состояние, которое можно передать на дисплей по P2P (UC3);
- slug файла задается при создании и не меняется при переименовании рутины; переименование меняет только `name`.

Поля `created`, `edited`, `executed` из рутины убираются: даты правок есть в git, последний запуск вычисляется из `runs/`. Сейчас каждый запуск модифицирует рутину (`executed`), что порождает лишние коммиты и конфликты.

### Запуск

```json
{
  "id": "ab12cd34",
  "routine": "warmup",
  "routineName": "3. Warmup",
  "startedAt": "2026-11-02T15:30:00Z",
  "finishedAt": "2026-11-02T15:36:07Z",
  "status": "completed",
  "activeSeconds": 352,
  "pausedSeconds": 15,
  "device": "d-7f3a"
}
```

- `status`: `completed` или `aborted`;
- `id` генерирует клиент, он же в имени файла → повторная отправка не создает дубль;
- шаги (план и факт) - позже, если понадобятся.

## 3. Синхронизация

Чтение:

1. `GET /repos/{repo}/branches/{branch}` с `If-None-Match` → `304`, если ничего не менялось (не тратит лимит).
2. Иначе `GET /git/trees/{sha}?recursive=1` → все пути и sha блобов.
3. Скачать только блобы, чьи sha изменились (`GET /git/blobs/{sha}`), декодировать base64 → UTF-8.
4. Пути, которых больше нет в дереве, удалить из локального кэша.

Запись:

- **Запуск:** `PUT contents/runs/...` без `sha`. Ответ "файл уже существует" (422) = успех. `409` = гонка с другим коммитом → повтор с задержкой.
- **Рутина:** `PUT` с `sha` версии, от которой начиналась правка. `409` → конфликт, UI показывает обе версии: "Взять ту", "Оставить мою".
- **Удаление рутины:** `DELETE` с `sha`, конфликт обрабатывается так же.

Офлайн: запуски попадают в outbox (localStorage) и отправляются при появлении сети и при каждом синке. Значок синка: "✓" или "↑ N".

Кэш: последнее дерево и содержимое файлов в localStorage → приложение открывается мгновенно и работает без сети.

## 4. Пользователи и доступ

### Модель

Пользователь - человек. У него роль, свой GitHub-токен и одно или несколько устройств.

| Роль | Права токена | Может | Кто |
| --- | --- | --- | --- |
| `owner` | Contents: read/write | Все, управляет пользователями | Вы |
| `writer` | Contents: read/write | Писать данные | Доверенные люди |
| `suggester` | Contents: read, Issues: write | Читать, предлагать через issues | Участники |
| `reader` | Contents: read | Читать | Зрители, дисплей (ТВ) |
| `guest` | Нет токена | Только то, что передает хост по WebRTC, пока хост в сети | Разовые гости, партнер на тренировке |

- Права `reader` и `suggester` ограничивает сам GitHub: такой токен не может ни записать, ни удалить, ни перезаписать историю.
- `writer` технически может перезаписать историю (защита веток для приватных репозиториев - только на GitHub Pro). Давать роль только тем, кому доверяете; страховка - зеркало (раздел 4.6).
- Токен у каждого пользователя свой: отозвать одного - не трогать остальных. Срок токена = срок доступа ("на неделю" = токен на 7 дней).
- Все токены создает владелец вручную на GitHub (API для этого нет) и передает в приглашении.
- Лимит API, насколько известно, общий на аккаунт владельца: для нескольких пользователей достаточно.

### Гость (`guest`)

Гость не получает токен и не попадает в `users/`. Он подключается по WebRTC к устройству пользователя, у которого есть доступ (хост), и видит только то, чем хост делится.

- **Подключение:** гостевая ссылка (см. "Ссылки" ниже). Пароль комнаты для сигнализации (Trystero) выводится из секрета → чужие не найдут комнату.
- **Что видит гость:** только переданное хостом - текущую рутину, идущий таймер, открытый документ. Не весь репозиторий, как `reader`.
- **Уровни внутри сессии:** смотреть (дисплей); управлять (пауза, следующий шаг); предлагать (гость отправляет запись или правку, хост решает и коммитит своим токеном). Права гостя никогда не выше прав хоста.
- **Жизнь сессии:** пока хост в сети. Хост закрыл приложение или нажал "Завершить" → гость отключен. Следов в репозитории не остается, кроме того, что хост закоммитил сам.
- **Сеть:** в одной комнате или Wi-Fi соединение прямое, TURN не нужен; интернет нужен только на секунды для сигнализации.
- **Сценарии:** ТВ или чужой планшет как дисплей (UC3) без выдачи токена; тренировка вдвоем (UC10); показать документ вживую.

### Формат

```
users/<user-id>.json
```

```json
{
  "id": "u-oleg",
  "name": "Oleg",
  "role": "owner",
  "token": { "fingerprint": "sha256:1f3a...", "expiresAt": null },
  "devices": [
    { "id": "d-7f3a", "name": "Pixel 9 Pro", "publicKey": "<JWK>", "addedAt": "2026-11-02T15:00:00Z" }
  ],
  "addedAt": "2026-11-02T15:00:00Z",
  "signature": "<подпись владельца>"
}
```

- `fingerprint` - хэш токена, сам токен в репозитории не хранится.
- Записи `users/` подписывает ключ устройства владельца. Клиенты игнорируют неподписанные или измененные записи: `writer` может технически переписать файл, но не подделать подпись.

### Первый запуск (владелец)

1. Настройки → "Подключить репозиторий".
2. Ссылка на создание fine-grained токена (по возможности с заполненными полями): только репозиторий данных, Contents read/write, без срока или максимальный.
3. Вставить токен в форму входа (`autocomplete` → менеджер паролей сохранит).
4. Приложение создает пару ключей устройства (WebCrypto, неэкспортируемый приватный ключ в IndexedDB) и коммитит `users/<id>.json` с ролью `owner`.

### Ссылки

Два типа ссылок. QR - это та же ссылка: для того, кто рядом; ссылка - для отправки в мессенджер. Если сканировать не может сам приглашаемый (ТВ), QR показывает он, а сканирует хост.

| | Гостевая ссылка | Инвайт-ссылка |
| --- | --- | --- |
| Адрес | `#/guest?room=<id>&k=<секрет>` | `#/invite?room=<id>&k=<секрет>[&t=...]` |
| Дает | Вход в живую сессию хоста | Постоянный доступ: пользователь или новое устройство |
| Токен | Никогда | Зависит от режима (ниже) |
| Использований | Много, пока идет сессия (группа на тренировке) | Одно |
| Срок | До конца сессии | До первого использования или 10 минут (в режимах со ссылкой - срок токена) |
| Подтверждение | Каждого гостя или "впускать всех" на время сессии | Каждого, по коду |
| След в репозитории | Нет | Запись в `users/` |

#### Гостевая ссылка

1. Хост: "Пригласить гостей" → уровень (смотреть, управлять, предлагать) → ссылка или QR.
2. Гость открывает → подключается к комнате по WebRTC → хост видит "Гость, код 4F2A" → впускает (или включен режим "впускать всех").
3. Хост завершил сессию или закрыл приложение → ссылка перестает работать.

#### Инвайт-ссылка

Для нового пользователя с токеном и для нового устройства существующего пользователя.

Ссылка: `#/invite?room=<id>&k=<одноразовый секрет>`, плюс, в зависимости от режима, токен.

Как передается токен - настройка приглашения (значение по умолчанию задается в настройках, отдельно для каждой роли):

| Режим | Ссылка содержит | Хост онлайн при входе | Перехват ссылки | Когда |
| --- | --- | --- | --- | --- |
| `p2p` | Только комнату и секрет | Нужен | Бесполезен без подтверждения | По умолчанию для `writer` |
| `link+pin` | Токен, зашифрованный секретом и PIN | Не нужен | Бесполезен без PIN; PIN сообщается отдельно | Асинхронно, но безопасно |
| `link` | Токен открыто (в части после `#`, на хостинг не уходит) | Не нужен | Дает доступ до отзыва или истечения токена | `reader` с коротким сроком |

Во всех режимах новое устройство регистрируется в `users/` только после подтверждения хостом по коду; в режимах `link` и `link+pin` подтверждение асинхронное - при следующем синке хоста. До подтверждения устройство уже может пользоваться токеном, но не попадает в ротации.

1. Хост: "Пригласить пользователя" → кого (новый пользователь или новое устройство существующего), роль, срок. Для ролей с токеном - вставить токен, созданный на GitHub с правами роли.
2. Приглашаемый открывает ссылку → устройство создает пару ключей → подключается к комнате по WebRTC (пароль комнаты выводится из секрета).
3. Оба показывают код проверки (отпечаток ключей сессии) → хост сверяет и подтверждает.
4. Дальше по роли:
   - роли с токеном в режиме `p2p` - хост передает токен по зашифрованному каналу, создает или дополняет запись `users/`, подписывает и коммитит;
   - в режимах `link` и `link+pin` шаги 2-3 не нужны для входа: токен берется из ссылки, а подтверждение кода - асинхронно.
5. Секрет действует до первого использования или 10 минут.

Если в режиме `p2p` WebRTC не соединился (разные сети без TURN), хост переделывает приглашение в `link+pin`.

Первое устройство владельца - единственное исключение: приглашать его некому, токен вставляется вручную (см. выше).

### Отключение

- **Пользователя:** отозвать его токен на GitHub → запись в `users/` помечается отключенной. Остальных не касается.
- **Одного устройства пользователя** (у него несколько устройств с общим токеном):
  1. Владелец или сам пользователь создает новый токен с теми же правами.
  2. Приложение шифрует его публичным ключом каждого оставшегося устройства этого пользователя → `.rotation/<device-id>.json`.
  3. Устройства при синке забирают новый токен и отмечаются; затем старый токен отзывается.
  4. Устройство, не успевшее переключиться, подключается заново по QR.
- Для `reader` ротация через репозиторий невозможна (он не пишет отметки) - проще выдать новое приглашение оставшимся устройствам.

### Границы защиты

- Удаленное устройство сохраняет доступ до отзыва старого токена.
- Пользователь с ролью `writer` может испортить данные, но не подделать записи `users/` и не скрыть это из истории без перезаписи; от перезаписи - зеркало.
- Утечка токена без отключения не ограничена по времени, кроме срока токена.
- Токен и приватный ключ живут в хранилище браузера: очистка данных сайта → подключение заново по QR.

### Зеркало

Регулярный `git fetch` репозитория данных на свой сервер (bublik или nl1, через infra) с refspec без `+`: перезапись истории не подхватывается, а вызывает уведомление. Данные переживают и порчу, и проблемы на стороне GitHub.

## 5. UX

- **Главная:** список рутин из кэша, значок синка, под каждой рутиной - последний запуск и серия дней.
- **Таймер:** как сейчас (голос, бипы, wake lock). При выходе до конца: "Сохранить как прерванный?". Запуски короче 30 с не сохраняются.
- **Редактор:** дерево, как сейчас, плюс вкладка "Текст" (YAML). Валидация одной схемой для обеих вкладок.
- **История:** лента запусков, фильтр прерванных; на странице рутины - количество, серия, тепловая карта, среднее активное время. Все считается на клиенте.
- **Изменения извне:** после синка тост "Обновлено извне: 3. Warmup".
- **Настройки:** репозиторий, голос и звук, Пользователи (список, роли, устройства, последний синк, пригласить, отключить).

## 6. Миграция

Скрипт `scripts/migrate.mjs <путь к клону репозитория данных>`:

- `routines/*.json` → `routines/<slug>.yaml`; для кириллических названий slug транслитерируется;
- `history.json` → `runs/YYYY/MM/*.json`: `durationSeconds` → `activeSeconds`, `pausedSeconds: 0`, `status: completed`; записи короче 30 с - `aborted`; запись на 6211 с - `aborted` (явно аномальная);
- старые файлы удаляются;
- результат - один коммит, который вы проверяете и пушите.

`git-routine-storage` (тестовый) - архивировать.
